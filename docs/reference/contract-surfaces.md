# Contract surfaces

Load-bearing names other code and tests depend on. A rename here is a breaking
change: grep the registry before touching one, and add a row when a new shared
entry point ships.

## Test harness

| Name                                        | File                          | Contract                                                                                                                                                                                                 |
| ------------------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createOwnerClient()`                       | `tests/helpers/auth.ts`       | Signs up a fresh, distinct owner and returns `{ client, userId, email, password }` — an anon-keyed client under that owner's RLS. Never service-role.                                                    |
| `createAuthenticatedCookieHeader()`         | `tests/helpers/session.ts`    | Mints a fresh owner and returns the genuine (possibly chunked) `sb-<host>-auth-token` Cookie header a browser would send.                                                                                |
| `createAuthenticatedOwner()`                | `tests/helpers/session.ts`    | As above, plus the owner's anon-keyed client, so a test can drive an authenticated route and verify its DB side-effect as the same owner.                                                                |
| `corruptCookieHeader(header)`               | `tests/helpers/session.ts`    | Turns a captured header into a present-but-invalid session, keeping the captured cookie name so the negative case cannot pass for the wrong reason.                                                      |
| `runMiddleware({ pathname, cookieHeader })` | `tests/helpers/middleware.ts` | Drives the real `src/middleware.ts` `onRequest` and returns `{ response, nextCalled, locals }`.                                                                                                          |
| `createAnonClient()`                        | `tests/helpers/auth.ts`       | An anon-keyed client with **no session**, so it carries the `anon` role — the caretaker's actual identity. The only way to assert what a link-holder can and cannot reach.                               |
| `createOwnerWithPet()`                      | `tests/helpers/auth.ts`       | An owner plus one pet, inserted through that owner's own client. Every care period needs at least one pet (S-08), so this is the seeding primitive for three suites; without it each grows its own copy. |
| `createAuthenticatedOwnerWithPet()`         | `tests/helpers/session.ts`    | The same, plus the genuine session Cookie header — for route tests that both drive a handler and need a pet the owner really owns.                                                                       |

| `care_slots` claim columns                      | `supabase/migrations/`           | `claimed_by_name`, `claimed_at` and `claim_digest` are ONE fact, tied by `care_slots_claim_complete`: all three null (free) or all three set (taken). `care_slots_claim_digest_format` pins the digest to 64 lowercase hex chars, because the reveal will be an equality test and a mixed-case digest would silently never match. Both constraints are live and pinned by `tests/rls/care-slots.isolation.test.ts`. `claim_digest` holds the hex SHA-256 of the caretaker's capability secret and answers "is this slot _mine_?", which `claimed_by_name` cannot (unbounded, non-unique, unverified). **`claim_slots` is its only _intended_ writer** (S-03 Phase 2) — the owner's `care_slots_update_own` policy plus their UPDATE grant on the table can still write these columns directly, read from `pg_policy` and `information_schema.role_table_grants`. `get_claimed_details` reads it (S-03 Phase 3): "which slots are mine" and "may I see the sensitive tier" are both an equality test on this column, scoped by `period_id` so a capability earned on one trip cannot open another. ⚠️ **One capability = one identity is NOT held by the schema.** Nothing stops one `claim_digest` from carrying two different `claimed_by_name` values in the same period (verified in psql; impl-review F1) — a multi-row invariant no CHECK can express. `claim_slots` is the **only** enforcement layer, the same posture as "at least one pet" in `create_period_with_slots`, and `tests/rls/claim-slots.test.ts` is the only thing that would notice it break. A direct owner UPDATE can still break it.                                                                                                                                                                                                                                                                                    |
| `care_periods.caretaker_note`                   | `supabase/migrations/`           | Free text about the TRIP rather than a pet (the design's NOTATKA). Written by `create_period_with_slots`, read back to the owner on `/periods/[id]`. Sensitive tier: served by `get_claimed_details` to a holder of a matching capability secret, and never by `get_period_by_token`, which builds a named `jsonb_build_object` that omits it (pinned by `tests/rls/invite-token.test.ts`). No caretaker sees it until they have claimed a slot on the trip.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `get_period_by_token`                           | `supabase/migrations/`           | The anon-reachable **read** door. It was the only anon-reachable surface until S-03 Phase 2 added `claim_slots` and Phase 3 added `get_claimed_details`; all three live under the same four rules in `docs/reference/data-access.md`, and none of them is an anon table policy. Security-definer; resolves at most one active period from a raw invite token and returns it with its slots' free/taken state and its pets carrying their **public** (`is_sensitive = false`) instruction rows. A period with no linked pets returns `pets: []`, never null — the caretaker page must render one. Returns NULL for unknown, malformed and revoked tokens alike. The exact top-level key set (`period`, `pets`, `slots`) is pinned by `tests/rls/invite-token.test.ts`, so widening it takes a deliberate test edit. A caretaker capability now extends the model by adding a sibling function under the same four rules, not by widening this one — see `claim_slots` above and `data-access.md` rule 2. Never an anon policy.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `get_claimed_details`                           | `supabase/migrations/`           | The sensitive tier of FR-008 (S-03 Phase 3). Security-definer, **stable**, `(p_token text, p_claim_secret text) returns jsonb`. Requires BOTH the invite token and a capability secret whose digest holds at least one claimed slot in that period; anything less returns NULL, so an unresolvable token, a wrong secret and a capability with no slots here are indistinguishable. Returns `{name, caretaker_note, slots, pets}` where `pets[].instructions` carries **only** `is_sensitive = true` rows — the public ones come from `get_period_by_token` and the page composes the two. Same four-role grant pair as the other doors.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `SPECIES_LABEL` / `SPECIES_OPTIONS`             | `src/lib/pet-format.ts`          | The Polish species names, in one place. | `MAX_CLAIMANT_NAME_LENGTH`                      | `src/lib/period-format.ts`       | The caretaker's name bound, 80 chars. The odd one out among the shared bounds: it mirrors a guard inside `claim_slots` (which raises `PT400` past it), **not** a column CHECK — `care_slots.claimed_by_name` is unbounded `text`, and that function is the only writer anon can reach, so its raise is the whole guarantee. | `claim_slots`                                   | `supabase/migrations/`           | The anon-reachable **write** door (S-03 Phase 2). Security-definer, **volatile**, `(p_token text, p_slot_ids uuid[], p_claim_secret text, p_name text default null) returns jsonb`. Takes the RAW capability secret and hashes it inside, exactly as it does the invite token, so `care_slots.claim_digest` is never itself a credential (Phase 2 impl-review F1). Derives the period from the invite token — it never accepts a period id, which is what makes a slot uuid from another period unusable. All-or-nothing: one guarded `update ... where claimed_by_name is null`, then the row count is compared to the request and a mismatch raises so the whole claim rolls back. Failure signalling is the one place rule 4 is deliberately widened: an unresolvable token returns NULL as the read door does, but a refusal raises `PT409` with the conflicting `{slot_date, time_of_day}` rows in DETAIL (PostgREST maps `PTxxx` onto the HTTP status; bad arguments raise `PT400`). On a follow-up claim the stored `claimed_by_name` wins and `p_name` is ignored.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `release_slot`                                  | `supabase/migrations/`           | The owner's **release** door (S-04 Phase 2). Security-**invoker**, volatile, `(p_period_id uuid, p_slot_id uuid) returns uuid` — unlike every anon-facing function here it runs as the caller, so `care_slots_update_own` is the authorization boundary and the body is only a guard. One `update … set claimed_by_name = null, claimed_at = null, claim_digest = null where id = p_slot_id and period_id = p_period_id and claimed_at is not null`, so the three claim columns can never be written apart. The `period_id` predicate is redundant with RLS and kept deliberately: it stops a slot uuid from another of the owner's OWN periods being released through the wrong period's endpoint. Returns the slot id, or **NULL** when the slot is not in that period, does not exist, RLS filtered it out, or it was already free — one answer for all four, and a scalar rather than a composite so a miss is honestly NULL. Grants: `authenticated` only; `anon` and `service_role` are revoked, pinned from both directions by `tests/rls/release-slot.test.ts` (42501, not an empty result). It is the only **intended** owner-side writer of the claim columns — but, exactly as the `care_slots` row above records, the owner's UPDATE grant plus `care_slots_update_own` still permit a direct write, so this is a convention the schema does not enforce. ⚠️ Nulling `claim_digest` has a **downstream** effect the caller must know about: `get_claimed_details` gates the sensitive tier on that column, so freeing one of several terms is harmless but freeing a capability's LAST term revokes that caretaker's reveal outright — intended, and unannounced to them by decision. No optimistic concurrency: a stale release can clobber a claim made after the page rendered (`prd.md` §Open Questions item 3). No caller yet: the owner-side route and island are S-04 Phase 3. |
