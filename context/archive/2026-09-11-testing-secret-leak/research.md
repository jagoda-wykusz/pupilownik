# Research: Risk #6 — secret leakage surfaces and gate wiring

**Date**: 2026-09-11T20:07:10+02:00
**Researcher**: jagoda.wykusz
**Git Commit**: `4af0dee` (pushed; permalink base `https://github.com/jagoda-wykusz/pupilownik/blob/4af0dee/`)

## Research Question

Rollout phase 3 of `context/foundation/test-plan.md`: prove that no Secret/service-role key reaches the built client bundle and that no secret or PII escapes in error bodies or logs, then wire the secret-leak grep as a CI gate (§5).

Scope agreed before research: the client bundle, error bodies and logs, and CI wiring. Out of scope: `.env` / git-history posture.

## Summary

Three findings reshape this phase, and each of them contradicts something the plan or the codebase currently asserts.

**1. The headline assertion cannot fail, and this is the same shape as the last change's phase 1.** Astro hard-fails the build when `astro:env/server` is resolved in a client environment (`ServerOnlyModule`), and there is no build-time value substitution anywhere in this pipeline — env is a runtime lookup against the worker's binding. A `dist/client` grep therefore cannot catch "the framework leaked the secret". It catches exactly two realistic mistakes: **a literal pasted into a client island**, and **a `PUBLIC_`-prefixed schema rename**, which is legal Astro and silently inlines the value. Those are worth a test; "secret-leak detection" oversells it.

**2. `dist/server/.dev.vars` contains the real `SUPABASE_URL` and `SUPABASE_KEY` as plaintext literals, on every build.** Verified directly. This is generated by `@cloudflare/vite-plugin` from `.env` / `process.env`. It is gitignored (`dist/`) and named in `dist/client/.assetsignore`, so it reaches neither git nor the asset bucket — a local-disk exposure, not a browser one. But it is decisive for assertion design: **a naive `grep dist/` would fail on a correct build**, and the reflex fix is to weaken the assertion.

**3. The live disclosure in this codebase is not in the bundle — it is `error.message` in a URL.** `src/pages/api/auth/signin.ts:16` and `signup.ts:16` put the raw GoTrue error into a query string. That discloses auth state ("Invalid login credentials" vs "Email not confirmed" vs "User already registered" — a user-enumeration oracle on signup), it persists in browser history, and `/auth` gets **no** `Referrer-Policy: no-referrer` — that header is scoped to `/invite` only (`src/middleware.ts:24`). This is squarely inside Risk #6's wording ("escapes into … error bodies") and nothing in the plan anticipated it.

And the finding that turned out to be bigger than Risk #6: **there is no CI at all.** `.github/workflows/ci.yml` ran lint + build on push/PR and was **deleted** in `b1fd059` in favour of a Cloudflare Workers Builds connection that — confirmed in the dashboard on 2026-09-11 — was never made. Nothing has run on push or PR since 2026-06-27. Every §5 row claiming a CI half describes a system that does not exist. See **Answered during research** below.

## Detailed Findings

### 1. The build artifact

**Shape, measured.** `dist/client/` — 29 files, all static assets (19 `.js`, 6 `.woff2`, 2 `.png`, 1 `.css`), **zero `.html`**. `dist/server/` — 51 files, the worker. The split is confirmed by the generated `dist/server/wrangler.json`, which points `assets.directory` at `../client` and `main` at `entry.mjs`. **A grep must target `dist/client/` only.**

**How env reaches code.** Only two vars are declared (`astro.config.mjs:41-46`), both `context: "server", access: "secret", optional: true`. `SUPABASE_SERVICE_KEY` is **not in the schema at all** — it exists only in tests, read from `process.env`. The built output shows a runtime lookup (`_internalGetSecret("SUPABASE_URL")`) bound per request from the Cloudflare runtime env; only the NAME appears in the bundle, never a value. There is no build-time inlining in this pipeline.

**The audit, measured with a positive control.** Every pattern returned zero hits in `dist/client/`: the literal key and URL values, `eyJ…` (JWT), `sb_secret_`, `sb_publishable_`, `service_role`, `supabaseKey`, `SUPABASE_SERVICE`, `supabase.co`, and even a case-insensitive `supabase`. The positive control matters: the same literal grep DOES find the value in `dist/server/.dev.vars`, so the tooling demonstrably works.

Worth stating because it inverts the usual expectation: **not even the publishable key or the project URL reach the browser.** In most Supabase apps both are designed to be public. Here the browser never talks to Supabase — `supabase-js` is bundled only into the worker, and the client islands call same-origin `/api/*`. The blast radius is smaller than the Supabase baseline, so an assertion here can be stricter than "no service_role key".

**Can the assertion ever fail?** Not through the framework path. Astro throws `ServerOnlyModule` at build time, and `EnvPrefixConflictsWithSecret` blocks the `import.meta.env` sweep route. It fails on:

- a literal hardcoded into a client island — the realistic mistake;
- a `PUBLIC_`-prefixed redeclaration with `context: "client", access: "public"` — legal, silent, and inlines the value. A **schema-shape assertion on `astro.config.mjs`** is what catches this before the bundle does.

**Token choice matters.** `service_role` is a poor grep token: it appears 5+ times as JSDoc prose inside bundled `supabase-js`, and is absent from `dist/client` today only because supabase-js is not client-bundled. The day an island imports it, that grep false-positives. Durable tokens: the literal value read from env at test time, `sb_secret_`, `eyJ[A-Za-z0-9_-]{10,}`, the project host.

**Instruction bodies cannot be build-embedded.** `grep -rn "prerender" src/` → 0 matches; the built manifest shows **22/22 routes `"prerender":false`**; `dist/client` holds 0 HTML files. All instruction data is read per request. The Polish strings that DO appear in `dist/client/_astro/*.js` are static UI chrome — form labels, validation copy, weekday abbreviations — authored in components, not data.

### 2. Error bodies and logs

**Every API route except the auth pair is disciplined.** Bodies carry fixed Polish sentences; logs carry `error.code` and `error.message` only, never `details`/`hint`. Per-route detail is in Code References below. Two routes deserve naming:

- `src/pages/invite/claim.ts:108` is the only route that reads `error.details`, and it parses rather than concatenates: `conflictMessage` JSON-parses the PT409 DETAIL and reformats, falling back to a generic sentence on anything unparseable. Measured over PostgREST, the DETAIL contains exactly `{slot_date, time_of_day}` and nothing else, with `[]` for a foreign slot. This is a deliberate, documented disclosure bounded by token possession — on the ledger, not a defect.
- `src/pages/api/pets.ts:29` is the only route still shipping `issues: parsed.error.issues`. Measured under zod v4: issues carry no `input` and no `received` value — an over-length instruction body yields only `{code, maximum, path, message}`. Safe today; it discloses schema shape and the caller's own field paths.

**The Postgres question, measured rather than reasoned.** Four route comments justify "log code and message, not the whole error" by claiming a Postgres error can carry the failing row. For these tables, **today, that is false** — and the measurement is a clean contrast:

- As `postgres` (bypasses RLS): `DETAIL: Failing row contains (…, Klucz pod wycieraczka kod 4821, …)` — the instruction body is there.
- As `authenticated` with RLS in force: **no DETAIL line at all.**

Postgres suppresses `Failing row contains` when RLS applies to the current user. All four tables have `relrowsecurity = t`, and `anon` holds zero table grants. End-to-end through PostgREST, every violation tested — unique on `token_digest`, three CHECK constraints, an RLS with-check — returned `details: null, hint: null`. **The digest is not in the unique-violation message either**, contrary to what four comments state.

The honest reading: **the practice is right, the stated reason is measurably false, and the practice still earns its place** — because it is the correct posture the moment a `BYPASSRLS` path, a `service_role` client in a handler, or a superuser-owned definer writer appears. That last one is not hypothetical in shape: a `SECURITY DEFINER` function owned by `postgres` **does** get the full row DETAIL, measured. `claim_slots`, `get_claimed_details`, `get_period_by_token` and `handle_new_user` are all `prosecdef = t` owned by `postgres`; none can currently violate a constraint, so the exposure is latent rather than live.

**The live findings, prioritized:**

1. **Raw GoTrue `error.message` in the URL** — `signin.ts:16`, `signup.ts:16`. Auth-state oracle; signup is a user-enumeration oracle. Persists in history and in `Referer`, because `/auth` receives neither `no-referrer` nor `no-store`. The only place in the app where a raw upstream error string reaches the caller.
2. **`Supabase is not configured` reaches an unauthenticated caller** — `signin.ts:11`, `signup.ts:11` (pre-auth), plus `pets.ts:17`, `periods.ts:22`, `token.ts:19`, `revoke.ts:69` for authenticated ones. An English string among Polish ones, stating server configuration state. `claim.ts:54` already shows the intended shape: "Nie udało się połączyć z serwerem".
3. **Constraint names in Cloudflare logs** — schema-shape disclosure to anyone with dashboard access. No row content.
4. **`claim_digest` selected into `periods/[id].astro:85`** — confined to frontmatter, guarded by `CaretakerLabel`'s prop type plus one source test. Astro serializes island props into HTML, so this is structurally sound today and one added field from not being.

### 3. CI and gate wiring

**What runs today**, verified against files rather than the document:

| Layer                            | What actually runs                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| per-edit agent hook              | `format-edited-file.mjs` (prettier), `related-tests.mjs` (scoped vitest, skips when the stack is down) |
| pre-commit (`.husky/pre-commit`) | `npx lint-staged` → `npx astro check`                                                                  |
| CI                               | **unverifiable from the repo**                                                                         |

`wrangler.jsonc` is 15 lines: name, adapter entrypoint, compatibility, the `ASSETS` binding pointing at `./dist`, observability. **No `build` field, no vars, no environments.** Nothing in the repo declares a build command — that is dashboard state on the connected Workers project.

**§5's gate table is wrong in three places.** It says typecheck runs `tsc --noEmit` in pre-commit — the hook has run `npx astro check` since 2026-09-07, and §5's own cost table below the table contradicts the row by listing `astro check` as "not wired". It credits lint and typecheck to "Cloudflare Workers Builds (wired)" — `astro build` neither lints nor typechecks `.astro` templates, and nothing chains those commands. It claims unit+integration run in CI — nothing runs vitest there, and the integration project needs a local Supabase stack Workers Builds does not have.

**Where a gate could live**, with the decisive constraint: to block a deploy rather than inspect an already-published artifact, the check must exit non-zero **inside the same command Workers Builds executes as its build step**.

- **npm script chained after build** (`"build": "astro build && node scripts/check-secrets.mjs"`) — the only option that both runs in CI and blocks before publish, _if_ the dashboard build command is the default `npm run build`. Also runs locally for free. Caveat: silently bypassable by editing the dashboard field.
- **A separate npm target invoked by Workers Builds** — requires a dashboard change no repo file records or verifies. That is precisely the failure mode §5 already fell into.
- **A vitest test shelling out to a build** — does not run in CI; would have to live in the `unit` project to work with Docker down; costs a full build per run. Local check only.
- **A pre-commit hook** — `dist/` is gitignored, so it either rebuilds (adding a full build to the ~40s `astro check`) or greps a stale artifact that does not correspond to the commit. Bypassable with `--no-verify`, and never enters the deploy path.

## Architecture Insights

- **The browser never talks to Supabase.** Islands call same-origin `/api/*`; `supabase-js` is worker-only. This is why the client bundle is cleaner than a normal Supabase app's, and it is the property an assertion should protect.
- **Env is a runtime binding, not a build-time value.** Nothing in this pipeline substitutes a secret into an artifact, which is why the artifact is clean and why the artifact test is weak.
- **Astro's env system is the real guard for Risk #6's headline**, and it guards by failing the build. Tests can assert the _schema shape_ that keeps that guard armed; they cannot usefully assert its output.
- **RLS suppresses Postgres's failing-row DETAIL**, which is a security property nobody wrote down and four comments contradict. It is also fragile in a specific way: it holds because of who the caller is, so it evaporates for a superuser-owned definer writer.
- **The disclosure discipline is uneven at exactly one seam**: every domain route returns fixed Polish sentences, while the two auth routes forward an upstream error verbatim into a URL. The auth routes predate the domain work.

## Answered during research

**Is a Cloudflare Workers Builds project connected? — NO.** Checked in the Cloudflare dashboard by the user, 2026-09-11. Nothing is connected to this repository.

This is the largest finding of the research and it is bigger than Risk #6. **This project has had no CI of any kind since 2026-06-27**, when `b1fd059` deleted a working `.github/workflows/ci.yml` in favour of a Workers Builds connection that was never made. Every gate that exists today is local: two per-edit agent hooks and a pre-commit hook. All of them are bypassable (`--no-verify`), none of them run for a clone that does not have the agent hooks configured, and nothing at all runs on push or on a pull request. The `lint`, `typecheck`, `build` and `unit + integration` rows in `test-plan.md` §5 that claim a CI half are not merely stale — **the CI column describes a system that does not exist**, and the "secret-leak grep on build output → CI, required after §3 Phase 3" row cannot be satisfied as written.

**Consequence for this phase, decided with the user:** scope narrows to the **assertion layer only**. The gate is built so that it runs locally and is ready to be wired the day CI exists, and §5 is corrected to say what is true rather than what was intended. Restoring CI is its own change — it is an infrastructure decision, not a test-rollout phase, and folding it in here would repeat the mistake `b1fd059` made in the other direction.

## Open Questions

1. **Are `SUPABASE_URL` / `SUPABASE_KEY` set anywhere for deployment?** Both are `optional: true`, so a build succeeds without them and a misconfigured deploy fails at runtime rather than at build time. Moot while nothing auto-deploys, live again the moment CI is restored.
2. **Is the auth-error-in-URL disclosure in scope for this change?** It is the one live finding, it is inside Risk #6's wording, and fixing it is a product change (swallow the upstream message, show a fixed sentence) rather than a test. It also removes a user-enumeration oracle on signup.
3. **Should the four false comments be corrected?** They justify correct practice with a hazard that does not exist for these tables. The risk is a future reader measuring the claim, finding it false, and removing the practice — at which point the latent definer-writer exposure has no guard.
4. **Does `dist/server/.dev.vars` warrant any action?** It is gitignored and not uploaded, so probably not — but it is a real plaintext secret on disk that a developer would not expect a build to write, and it is the reason the assertion must be scoped.
