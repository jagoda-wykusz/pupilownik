# Secret-Leak Assertions (Risk #6) Implementation Plan

## Overview

Deliver the three assertions rollout phase 3 owes Risk #6 — and state honestly what each one is worth, because research measured that **none of them is the thing the test plan named**. The client-bundle grep cannot catch a framework leak; the real disclosure is an upstream error message in a URL; and the CI gate has nowhere to live because there is no CI. Fix the one live leak, build the checks so they run today and wire in one line the day CI returns, and correct the two places where prose describes a system that does not exist.

## Current State Analysis

Everything below was measured during `research.md`, not inferred.

**The client bundle is clean, and structurally so.** `dist/` splits into `client/` (29 files, browser-served) and `server/` (51 files, the worker) — confirmed by the generated `dist/server/wrangler.json`, which points `assets.directory` at `../client`. Every pattern returned zero hits in `dist/client/`: the literal key and URL values, `eyJ…`, `sb_secret_`, `sb_publishable_`, `service_role`, `supabase.co`, even a case-insensitive `supabase`. Not even the publishable key reaches the browser, because the browser never talks to Supabase — `supabase-js` is worker-only and islands call same-origin `/api/*`.

**The env schema is the real guard.** `astro.config.mjs:41-46` declares exactly two vars, both `context: "server", access: "secret", optional: true`; `SUPABASE_SERVICE_KEY` is not in the schema at all. Astro emits a runtime lookup bound per request from the worker env — there is **no build-time value substitution anywhere in this pipeline**, so only the NAME appears in any bundle.

**`dist/server/.dev.vars` carries the real values in plaintext, on every build.** Generated by `@cloudflare/vite-plugin` from `.env`. Gitignored and listed in `dist/client/.assetsignore`, so it reaches neither git nor the asset bucket. Decisive for this plan: **a `grep dist/` would fail on a correct build**, and the reflex fix is to weaken the assertion.

**The live disclosure is in a URL, not an artifact.** `src/pages/api/auth/signin.ts:16` and `signup.ts:16` put the raw GoTrue `error.message` into a query string; `:11` in both does the same with `"Supabase is not configured"`. This discloses auth state — and on signup it is a user-enumeration oracle. It persists in browser history and in `Referer`, because `Referrer-Policy: no-referrer` is scoped to `/invite` only (`src/middleware.ts:24`). Every other route answers with fixed Polish sentences and logs `error.code` + `error.message` only.

**Four route comments justify correct practice with a false reason.** Postgres suppresses the `DETAIL: Failing row contains (...)` description when RLS applies to the caller. Measured as a contrast: as `postgres` the instruction body appears in the DETAIL; as `authenticated` there is no DETAIL line at all. Through PostgREST, every violation tested — unique on `token_digest`, three CHECKs, an RLS with-check — returned `details: null`. The hazard those comments name does not exist for these tables today. It **does** exist for a `SECURITY DEFINER` function owned by `postgres`, which gets the full row DETAIL (measured) — so the practice is right and the stated reason must change.

**There is no CI.** Confirmed in the Cloudflare dashboard, 2026-09-11: no Workers Builds project is connected. `.github/workflows/ci.yml` ran lint + build on push/PR and was deleted in `b1fd059` in favour of that connection. Nothing has run on push or PR since 2026-06-27; every gate today is local and bypassable.

### Key Discoveries:

- `astro.config.mjs:41-46` — the schema is the guard; a `PUBLIC_`-prefixed redeclaration with `context: "client"` is legal Astro and silently inlines the value, and it is the one realistic mistake a bundle grep catches only after the fact.
- Astro hard-fails the build on a client-side `astro:env/server` import (`ServerOnlyModule`) and on a secret name colliding with `vite.envPrefix` (`EnvPrefixConflictsWithSecret`) — which is why the bundle assertion cannot fail through the framework path.
- `service_role` is a poor grep token: it appears 5+ times as JSDoc prose inside bundled `supabase-js`, absent from `dist/client` today only because supabase-js is not client-bundled.
- `src/pages/invite/claim.ts:54` already answers a missing-config with a neutral Polish sentence — the pattern the auth routes should copy.
- 22/22 routes are `"prerender":false` and `dist/client` holds zero HTML, so instruction bodies cannot be build-embedded at all.

## Desired End State

Three checks exist and each says what it is worth. A `PUBLIC_` rename or a hardcoded literal fails a test. Signing in with a wrong password, an unknown address and an unconfirmed email produce one identical sentence, and nothing from the upstream error reaches the URL. `test-plan.md` §5 describes the gates that exist; the four route comments justify their practice with the reason that is actually true.

Verified by: `npm test` green, `npm run check:secrets` green, and a mutation pass per phase.

## What We're NOT Doing

- **Not restoring CI.** No GitHub Actions workflow, no Workers Builds connection. That is an infrastructure decision and its own change; folding it in here repeats `b1fd059`'s mistake in the other direction. The checks are built to wire in one line when it happens.
- **Not chaining the check into `npm run build`.** It stays a separate script plus a test, so a failing check never blocks an unrelated local build.
- **Not touching the four authenticated routes** that answer `"Supabase is not configured"` (`pets.ts:17`, `periods.ts:22`, `token.ts:19`, `revoke.ts:69`). They disclose configuration state only to a signed-in owner — lower severity than the pre-auth pair, and English-among-Polish is a cosmetic inconsistency. Recorded in §7 instead.
- **Not acting on `dist/server/.dev.vars`.** Gitignored, not uploaded; its only consequence for us is that the script must target `dist/client`, which it does. §7 entry only.
- **Not changing `pets.ts`'s `issues: parsed.error.issues`.** Measured safe under zod v4 (no `input`, no `received` in any issue). §7 entry naming the zod-version dependency.
- **Not mapping GoTrue error codes to Polish sentences.** One sentence for every sign-in failure was the decision; a code map would keep the oracle and add maintenance.
- **No e2e, no new runner, no `pg` client.**

## Implementation Approach

Three phases, ordered by how much each one can actually fail. Phase 1 builds the artifact and schema checks — cheap, structural, and honest about their narrow reach. Phase 2 is the only phase that changes user-visible behaviour and the only one closing a live disclosure. Phase 3 corrects the prose that this change measured to be false.

## Critical Implementation Details

**Debug & observability.** A build-artifact test that silently passes on a missing or stale `dist/` is worse than no test. The check must assert its own **positive control** — grep a string known to be present in `dist/client` — and the test must fail loudly, not skip quietly, if `dist/client` is absent. This is the same class of defect as the previous change's unfalsifiable assertion.

**Never read a success criterion's exit code through a pipe** — it is the pipe's code. Write to a file and read it back (`lessons.md`). Task-runner notifications wrapping a compound command have twice reported `exit 0` for a failing lint in this project.

## Phase 1: The artifact and the schema

### Overview

Build the secret check as a standalone script, run it from a unit test, and add the schema-shape assertion that catches the one mistake the grep would catch too late.

### Changes Required:

#### 1. The check script

**File**: `scripts/check-client-bundle.mjs` (new)

**Intent**: Scan the browser-served artifact for anything that must never reach it, and fail loudly rather than silently when there is nothing to scan. Exists as a script rather than only a test so it can be wired into CI in one line the day CI exists.

**Contract**: Reads `dist/client/` recursively. Fails on: the literal values of `SUPABASE_URL` and `SUPABASE_KEY` read from the environment at run time; `sb_secret_`; a JWT shape (`eyJ[A-Za-z0-9_-]{10,}`); and the Supabase project host. Deliberately does NOT scan `dist/server/` — `.dev.vars` there holds real values by design. Deliberately does NOT grep `service_role`, which is JSDoc prose inside `supabase-js`. Exits non-zero with the offending file and pattern; exits non-zero with a distinct message when `dist/client` is missing or empty. Asserts a positive control (a string known to be in the bundle) before reporting success, so an empty scan can never read as a pass. Wired as `npm run check:secrets`.

#### 2. The test that runs it

**File**: `tests/unit/client-bundle.test.ts` (new, `unit` project — no Docker)

**Intent**: Put the check inside `npm test` so it is not a script nobody runs, while keeping the honest limit visible: it inspects whatever build happens to be on disk.

**Contract**: Invokes the script and asserts exit zero. When `dist/client` is absent, the test **fails** with a message naming `npm run build` as the fix — it does not skip. The file header states what the check can and cannot catch: not a framework leak (Astro fails the build first), only a hardcoded literal in a client island.

#### 3. The schema-shape assertion

**File**: `tests/unit/env-schema.test.ts` (new, `unit` project)

**Intent**: Catch the one realistic mistake before it reaches an artifact — a `PUBLIC_`-prefixed redeclaration with `context: "client"`, which is legal Astro, silent, and inlines the value into the client bundle.

**Contract**: Reads `astro.config.mjs` and asserts that every entry in `env.schema` carries `context: "server"` and `access: "secret"`, and that the schema contains no `context: "client"` entry at all. Names in the test title why a source-text assertion is the right tool here: the property is about configuration intent, and the alternative — importing the config — would evaluate adapter and font providers for a two-field check.

### Success Criteria:

#### Automated Verification:

- Check passes on a fresh build: `npm run build` then `npm run check:secrets`
- Unit project passes: `npx vitest run --project unit`
- Full suite passes: `npm test`
- Lint passes: `npm run lint`
- Type check passes: `npx astro check`

#### Manual Verification:

- Mutation check: paste the publishable key literal into a client island; `check:secrets` fails naming the file. Restore.
- Mutation check: add a `PUBLIC_SUPABASE_KEY` entry with `context: "client"` to the schema; the schema test fails. Restore.
- Mutation check: delete `dist/client`; the test fails with the build instruction rather than passing or skipping.

**Implementation Note**: After automated verification passes, pause for manual confirmation before Phase 2.

## Phase 2: The auth routes stop forwarding upstream errors

### Overview

Close the one live disclosure: no GoTrue message, and no configuration state, reaches the URL.

### Changes Required:

#### 1. Sign-in and sign-up

**File**: `src/pages/api/auth/signin.ts`, `src/pages/api/auth/signup.ts`

**Intent**: Replace both forwarded strings with one fixed Polish sentence per route, so a wrong password, an unknown address and an unconfirmed email are indistinguishable. The upstream error stays in the server log, where it is useful and not caller-visible.

**Contract**: Neither route puts `error.message` nor a configuration fact into the redirect target. One sentence per route, identical across every failure cause. The missing-config branch answers with the same neutral sentence, following `src/pages/invite/claim.ts:54`. Add a `console.error` carrying the upstream message so the information is not lost — matching the `code, message` discipline every other route uses. The `?error=` mechanism and `SignInForm`/`ServerError` rendering are untouched.

#### 2. The tests

**File**: `tests/api/auth-error-disclosure.test.ts` (new, `integration` project)

**Intent**: Pin that the upstream message cannot come back, and that the pre-auth surface says nothing about server configuration.

**Contract**: Drive the real handlers with a genuine local stack. Cases: a wrong password, an unknown address and an unconfirmed account all redirect to the **same** `Location` — compared as whole strings, not by prefix; the `Location` contains none of GoTrue's wording; and no route reachable without a session mentions configuration state. Assert the sentence is the one the UI shows, so a copy change that reintroduces branching fails here.

### Success Criteria:

#### Automated Verification:

- New file passes: `npx vitest run --project integration tests/api/auth-error-disclosure.test.ts`
- Full suite passes: `npm test`
- Lint passes: `npm run lint`
- Type check passes: `npx astro check`

#### Manual Verification:

- Mutation check: restore `error.message` into either redirect; the whole-string comparison fails.
- Sign in by hand with a wrong password and with an unknown address — the page shows the same sentence and the URL carries no upstream text.
- The upstream message is visible in the server log.

**Implementation Note**: Pause for manual confirmation before Phase 3.

## Phase 3: Correct the prose this change measured

### Overview

Four comments justify a correct practice with a false reason; §5 describes a CI that does not exist. Both are the output of this phase's measurements.

### Changes Required:

#### 1. The four route comments

**File**: `src/pages/api/periods.ts`, `src/pages/api/periods/[id]/token.ts`, `src/pages/api/periods/[id]/slots/[slotId]/release.ts`, `src/pages/invite/claim.ts`

**Intent**: Keep the practice, replace the reason. Each comment claims a Postgres error can carry the failing row; measured, RLS suppresses that DETAIL for every role this app uses.

**Contract**: State the measured fact (RLS suppresses `Failing row contains`; every violation tested returned `details: null`, including the unique violation on `token_digest`, contrary to what these comments say), and the reason the practice still stands: a `SECURITY DEFINER` function owned by `postgres` **does** receive the full row DETAIL, and four such functions exist. Keep it to a few lines per site; do not restate the whole measurement in four places.

#### 2. `test-plan.md` §5 and the gate inventory

**File**: `context/foundation/test-plan.md`

**Intent**: §5 claims CI-enforced gates for lint, typecheck, build and tests. There is no CI. It also says the pre-commit hook runs `tsc --noEmit`; it has run `astro check` since 2026-09-07, and §5's own cost table contradicts its table.

**Contract**: Rewrite the gate table to describe what runs: two per-edit agent hooks, a pre-commit hook (`lint-staged` then `astro check`), and nothing else. State plainly that no CI exists, when it stopped existing and why, so the next reader does not plan around a phantom. Move the secret-leak row from "required after Phase 3" to a named, ready-to-wire local check. Mark §3 Phase 3 complete with this change folder.

#### 3. §6.6 and §7

**File**: `context/foundation/test-plan.md`

**Contract**: §6.6 gains a note for this phase. §7 gains entries for: the four authenticated routes still disclosing configuration state to a signed-in owner; `dist/server/.dev.vars` and why it is not acted on; `pets.ts`'s zod `issues` and the zod-version dependency that makes it safe; and the honest reach of the bundle check — that it cannot catch a framework leak because Astro fails the build first, so its value is the hardcoded-literal case.

#### 4. Close the change

**File**: `context/changes/testing-secret-leak/change.md`

**Contract**: `status: implemented`, `updated` stamped. No roadmap item matches a test-rollout phase.
